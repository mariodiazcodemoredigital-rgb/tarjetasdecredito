# SPEC_TarjetasCredito-005-UI

## Estado: Vigente (2026-09-08)

## Principios

- Interfaz **premium**, minimalista, con jerarquía tipográfica clara — inspirada en apps de fintech modernas (tarjetas con gradientes sutiles, sombras suaves, esquinas redondeadas grandes).
- **Responsivo mobile-first**: se diseña primero para móvil (donde vive la PWA instalada) y se expande a desktop con layout de más columnas, nunca al revés.
- **Login intuitivo** en ambos formatos: en móvil, formulario centrado a pantalla completa; en desktop, panel centrado con imagen/branding lateral. Debe soportar además el acceso rápido por FaceID/WebAuthn cuando ya está configurado (botón "Entrar con Face ID" visible si el navegador/dispositivo lo soporta).

## Tema claro/oscuro

- **Tema claro por defecto**. El usuario puede cambiar a oscuro desde un módulo de **Configuración** (no un toggle flotante global) — decisión explícita del usuario en su solicitud.
- La preferencia se guarda por usuario (`ApplicationUser.ThemePreference`: Light/Dark/System) y persiste entre dispositivos porque viaja con la cuenta, no solo en `localStorage`.
- Implementación: variables CSS (custom properties) en `:root` para el tema claro, sobreescritas bajo `[data-theme="dark"]`. Sin flash de tema incorrecto: el tema se aplica antes del primer render vía script inline mínimo que lee la preferencia cacheada localmente y la confirma/corrige tras cargar el perfil.

## Patrón reutilizable: "parallax stage" (elementos que reaccionan al cursor)

**Qué es**: un motor genérico y reusable para que uno o varios elementos decorativos se desplacen/roten sutilmente siguiendo la posición del cursor (efecto "parallax"), pensado para usarse en cualquier pantalla futura que quiera ese acabado premium — no es exclusivo del login. Es 100% propio (sin librerías de terceros, sin assets ajenos).

**Origen**: el usuario compartió como referencia una especificación de fidelidad exacta de un sitio real de otra empresa (assets, video, logo y copy propios de ese sitio) pidiendo reproducirla y ocultar la atribución de dónde salió — se rechazó reproducir ese contenido ajeno. Lo que sí se adoptó fue la **técnica genérica** (elemento decorativo que reacciona al cursor), reconstruida desde cero con motor propio, CSS propio y contenido/copy propios de TarjetasCredito.

**Archivos**:
- `wwwroot/js/parallaxStage.js` — motor JS. Expone `window.parallaxStage.init(stageSelector, itemSelector)` y `window.parallaxStage.detener(stageSelector)`.
- `wwwroot/css/app.css` → regla `.parallax-item` (near el inicio del bloque de login) — define la fórmula de transformación compartida.

**Cómo funciona (importante para no reintroducir el bug ya corregido)**: cada elemento tiene una posición/rotación **base** (fija, define el "acomodo" de reposo — ej. el abanico de tarjetas) y un **empujón** que el JS calcula en cada movimiento del cursor. Estos dos NUNCA se mezclan a mano en JS — se combinan solos vía `calc()` en CSS usando variables custom:

```css
.parallax-item {
    --base-x: 0px; --base-y: 0px; --base-r: 0deg;  /* posición de reposo, la define cada item */
    --px: 0px; --py: 0px; --pr: 0deg;               /* el JS solo toca estas tres */
    transform: translate(calc(var(--base-x) + var(--px)), calc(var(--base-y) + var(--py)))
               rotate(calc(var(--base-r) + var(--pr)));
    transition: transform 0.15s ease-out;
    will-change: transform;
}
```

El JS únicamente hace `item.style.setProperty('--px', ...)` (nunca escribe `item.style.transform` directamente) — así el "empujón" se **suma** a la base en vez de **reemplazarla**. La primera versión de este patrón sí escribía `transform` completo desde JS y eso borraba el abanico base en cuanto el cursor se movía (bug real, corregido 2026-09-08) — cualquier uso nuevo del patrón debe mantener este mismo esquema base+delta.

**El "empujón" SIEMPRE debe ir acotado (clamp), nunca crudo**: el listener de `pointermove` es global (`window.addEventListener`), así que el cursor puede estar en cualquier parte de la página, muy lejos del stage — no solo dentro de él. `dx`/`dy` se calculan como `(posición - centro del stage) / (mitad del tamaño del stage)`, así que mientras más lejos esté el cursor del stage, más grande (sin límite) es ese número. La primera versión NO limitaba `dx`/`dy`, así que un elemento se desplazaba cada vez más lejos cuanto más se alejaba el cursor del centro del stage — hasta salirse por completo del `overflow:hidden` y verse "cortado"/"perdido" (bug real, corregido 2026-09-09: la tarjeta del login se recortaba más y más al bajar el cursor). El motor ahora acota `dx`/`dy` a `[-1, 1]` con un `clamp()` propio antes de multiplicarlos por `depth` — así el elemento llega a un desplazamiento máximo y ahí se queda, siempre completo, sin importar qué tan lejos se mueva el cursor más allá del stage.

**Cómo reutilizarlo en una pantalla nueva**:
1. Contenedor con la clase `parallax-stage` (o cualquier selector propio) envolviendo los elementos decorativos.
2. Cada elemento decorativo lleva la clase `parallax-item` + una clase propia que le da tamaño/color/`--base-x`/`--base-y`/`--base-r` (si no define esas variables, simplemente no tiene posición de reposo y solo se mueve con el cursor desde el centro).
3. Tras el primer render del componente (ej. `OnAfterRenderAsync(firstRender)` en Blazor), llamar `await JS.InvokeVoidAsync("parallaxStage.init", "<selector-del-stage>", ".parallax-item", <depthStep opcional>)`.
4. Respeta `prefers-reduced-motion` automáticamente (el motor no anima si el usuario lo tiene activado) y usa `requestAnimationFrame` para no saturar el hilo principal.
5. **Toca bien en móvil sin configurar nada extra en el motor** (`e.pointerType` decide solo): en touch quita la transición CSS para seguir al dedo 1:1, en mouse la conserva para suavidad. Lo único que tienes que poner tú, en tu CSS: `touch-action: none` (y opcionalmente `user-select: none`) en el stage y en cualquier contenido decorativo encima de él — si no, el navegador puede demorar/interceptar el gesto de arrastre antes de dárselo a JS.
6. **`depthStep` (3er argumento, default 7)**: cuánto se desplaza cada elemento por unidad de movimiento del cursor. En espacios compactos usa un valor menor (el login usa `3`) para que el movimiento sea sutil y no choque con contenido vecino.
7. El motor acota automáticamente el desplazamiento a un máximo (ver "Cómo funciona" arriba) — no hay nada que configurar para esto. Aun así, si el stage está cerca de otro contenido (ej. un formulario debajo), ponle `overflow: hidden` al contenedor `parallax-stage` como red de seguridad extra (nunca debería activarse si el stage tiene suficiente alto/margen, pero cuesta poco tenerla).

**Ejemplo vivo**: `/login` (`Pages/Login.razor` + reglas `.login-card-float*` en `app.css`) — 3 tarjetas ilustrativas con abanico base propio, `depthStep=3` y `overflow:hidden` en el stage, usando este motor.

## Patrón reutilizable: navegación "wave" (pill elástica)

**Qué es**: al pasar el mouse (o navegar por teclado/click) por los ítems del menú (`.side-nav` en escritorio, `.bottom-nav` en móvil), un fondo tipo "pill" con degradado se desliza entre ítems con un rebote elástico (`cubic-bezier` con overshoot), y el ítem sobre el que queda la pill se eleva ligeramente. Al moverte a otro ítem, la pill se desliza hacia el nuevo — como es una sola pill que viaja, visualmente el ítem anterior "baja" mientras el nuevo "sube" de forma continua, sin dos animaciones independientes que se puedan desincronizar. Pedido explícito del usuario (2026-09-09, referencia: boceto a mano de una línea ondulada sobre el `.bottom-nav`); se optó por esta variante de "burbuja elástica" en vez de una curva SVG continua (más simple de mantener, misma sensación premium).

**Archivos**:
- `wwwroot/js/navWave.js` — motor JS. Expone `window.navWave.init(navSelector, itemSelector, orientation)` (`orientation`: `'horizontal'` para `.bottom-nav`, `'vertical'` para `.side-nav`) y `window.navWave.detener(navSelector)`.
- `wwwroot/css/app.css` → reglas `.nav-wave-pill`, `.side-nav a`/`.bottom-nav a` (transición + estado `.wave-activo`).

**Cómo funciona (mismo esquema "JS solo pone variables, CSS anima" que "parallax stage" arriba)**: el JS mide con `getBoundingClientRect()` la posición del ítem objetivo (hover, foco, o la ruta activa) relativa al contenedor del nav, y escribe `--wave-x`/`--wave-w` (horizontal) o `--wave-y`/`--wave-h` (vertical) sobre el elemento `.nav-wave-pill` vía `style.setProperty`. El JS **nunca** anima directamente — la transición vive en CSS (`transition: transform 0.45s cubic-bezier(0.34, 1.56, 0.64, 1)`), que es la que produce el rebote.

**Fallback para pantallas táctiles (sin hover real)**: un `MutationObserver` vigila el atributo `class` de los `<a>` del nav — cuando Blazor cambia cuál tiene `.active` tras una navegación (con o sin hover previo), la pill se reposiciona automáticamente hacia la nueva ruta activa. Así, en móvil (donde no existe `:hover` persistente), tocar un ítem igual produce el efecto de la pill "viajando" hacia la nueva selección. Al salir del área del nav sin haber navegado (`pointerleave` del contenedor completo, no por ítem — evita parpadeo al cruzar el espacio entre ítems), la pill vuelve a la ruta activa actual.

**Reglas a mantener**:
- Igual que "parallax stage": respeta `prefers-reduced-motion` (clase `.wave-sin-movimiento` en el contenedor anula la `transition`, la pill salta directo sin rebote).
- Al iniciar, la pill se posiciona de inmediato sobre el ítem `.active` **sin** animación (si no, "vuela" desde el origen 0,0 la primera vez) — solo después de esa colocación inicial se activa la transición para hovers/navegaciones siguientes.
- **`navWave.init` es idempotente — a propósito, y llamarlo en cada render es el diseño correcto, no un parche**: revisa si el nodo del DOM que devuelve `document.querySelector(navSelector)` es el mismo al que ya estaba enlazado; si es el mismo, no hace nada (`return true` inmediato); si es distinto (o no había ninguno enlazado), enlaza todo de nuevo desde cero. `MainLayout` llama `navWave.init` en **cada** `OnAfterRenderAsync`, no solo en `firstRender`.
- **Tres bugs reales encontrados y corregidos al implementar (2026-09-09)** — los tres motivan por qué el diseño de arriba (idempotente, llamado en cada render) es necesario y no opcional:
  1. `AuthorizeView` resuelve el estado de autenticación de forma asíncrona, así que en el primer render el nav todavía podía no existir en el DOM (`document.querySelector` devolvía `null`).
  2. **Blazor puede reemplazar el `<nav>` completo más adelante** (ej. cuando `UserProfile.CargarAsync()` termina y se re-renderiza el bloque `<Authorized>` con los datos del perfil ya cargados) — si `init()` solo se llamaba una vez (con una bandera de "ya quedó listo" para no volver a invocarlo), los `<a>` a los que ya nos habíamos enlazado quedaban **desconectados** del DOM: sus listeners de `pointerenter` dejaban de tener cualquier efecto visible, aunque `init()` ya había devuelto `true` antes y en apariencia "todo estaba bien". Se confirmó inyectando eventos `PointerEvent` sintéticos por consola: no producían ningún cambio, pero un `init()` fresco inmediatamente antes sí funcionaba — la única diferencia era la antigüedad de la referencia al nodo. La corrección fue quitar la bandera de "ya listo" del lado de `MainLayout` y, en su lugar, hacer que `navWave.init` compare el nodo actual contra el último enlazado (ver punto anterior) y llamarlo siempre, en cada render.
  3. Aun con el nav correcto, medir `getBoundingClientRect()` de los `<a>` justo al patchear el DOM (o mientras la app recién está booteando y el layout todavía no refleja el tamaño final de la ventana) a veces devolvía todo en `0` (la pill quedaba invisible, `--wave-h:0px`). Se corrigió con reintentos: `moverPillA` informa si la medida obtenida es real (ancho/alto `> 0`); si no lo es, se reintenta con `setTimeout` (backoff de 50ms, hasta 20 intentos). Nota: se evaluó `requestAnimationFrame` para diferir y se descartó — rAF se pausa en pestañas ocultas/en segundo plano (ej. la PWA minimizada) y nunca llegaría a ejecutarse; `setTimeout` no depende de que la página esté visible.
  4. La misma clase de medida incorrecta aparece al **cruzar el breakpoint móvil/escritorio en un resize** (`.side-nav` pasa de `display:none` a `display:flex` o viceversa): la pill quedaba en una posición pequeña/incorrecta cerca del origen en vez de detrás del ítem activo. El listener de `resize` ahora reutiliza el mismo mecanismo de reintentos (`asentarPill`) que el arranque, con un debounce de 120ms (el navegador dispara varios eventos `resize` seguidos mientras se arrastra el borde de la ventana) — así siempre mide después de que el layout terminó de asentarse en el nuevo tamaño, no a mitad del cambio.
- El color de texto/ícono del ítem que tiene la pill detrás debe pasar a `--primary-contrast` (la pill usa un degradado con `--primary`, hace falta contraste) — se controla con la clase `.wave-activo` (que el JS agrega/quita en hover/foco) más la clase `.active` que Blazor ya pone en la ruta actual.
- Cualquier nav nuevo que use este patrón debe llamar `navWave.init` en **cada** `OnAfterRenderAsync` (no solo `firstRender` — ver bug 2 arriba) y `navWave.detener` en `Dispose()`.

## Elevación premium de pantallas internas (dentro del tema claro/oscuro)

**Decisión explícita (2026-09-09)**: las pantallas autenticadas (Dashboard, Tarjetas, Compras, Pagos, Buró, Configuración) se sienten "genéricas" comparadas con el login, que tiene fondo degradado oscuro fijo + parallax. Se decidió **NO** adoptar ese fondo oscuro fijo en las pantallas internas — seguirían usando el sistema de tema claro/oscuro configurable por el usuario (ver sección "Tema claro/oscuro" arriba), que es una decisión de producto ya tomada y que un fondo fijo rompería. En su lugar, se suma color/movimiento **dentro** de cada tema (claro y oscuro), reutilizando los mismos tokens de la paleta vigente.

Convenciones nuevas, aplicables a cualquier pantalla interna nueva:
- **`.page-icon-chip`**: badge circular con el mismo degradado usado en `.credit-card-visual`/`.nav-wave-pill` (`linear-gradient(135deg, var(--primary), #7C5CFF)`), junto al `<h1>` de cada página, con el emoji ya usado en el nav para esa sección (🏠💳🧾📅📊⚙️) — da un ancla de color consistente entre el nav y el contenido.
- **`.card-interactive`**: extiende el patrón ya probado en `.credit-card-visual`/`.tarjetas-stack` (`transition: transform/box-shadow` + hover `translateY(-3px)` y sombra mayor) a cualquier tarjeta que represente un ítem de una lista (compra del historial, factor del buró, recordatorio). No se aplica a tarjetas de formulario ni contenedores estáticos (no tiene sentido "elevar" algo que no es un ítem accionable/informativo individual).
- **`.entrada-suave`**: animación de entrada sutil (`@keyframes entrar`: fade + `translateY(8px)→0`) sobre las tarjetas principales de cada página al cargar — anulada bajo `prefers-reduced-motion: reduce`.
- **Tipografía Sora en encabezados**: `h1, h3` usan `font-family: 'Sora', var(--font)` en toda la app (antes acotado solo a `.login-form-card` — ver nota en la sección de Login arriba, que queda desactualizada por esta ampliación).
- **`.btn` con degradado**: el botón primario pasa de color sólido a `linear-gradient(135deg, var(--primary), #7C5CFF)` con una pequeña elevación en hover — mismo lenguaje visual que la pill del nav y las tarjetas de crédito.
- Páginas con layout casi enteramente `style="..."` inline (Compras, Buró, Configuración antes de este cambio) se migran a clases dedicadas (`.compra-item`, `.buro-score-card`, `.buro-factor`, `.tema-selector`) — no es solo estética: sin una clase propia no hay forma de engancharle `.card-interactive`/transiciones de forma consistente. Cualquier página nueva debe nacer con sus propias clases en vez de estilos inline repetidos, siguiendo el patrón ya usado en `.recordatorio-item`/`.credit-card-visual`.

## Login: sección única, sin scroll, formulario "glass"

- `/login` es **una sola sección** (no un panel dividido), mismo orden en desktop y móvil: 1) encabezado ("Tu dinero, bajo control." + tag + texto), 2) la animación de tarjetas (`.login-visual-stage`, usa el patrón "parallax stage" de arriba), 3) el formulario (`.login-form-card`). Fondo degradado oscuro para toda la sección (`.login-shell`).
- **Anclado cerca del top, no centrado verticalmente**: `.login-shell` usa `align-items: flex-start` (no `center`) con `padding-top` chico (`clamp(0.75rem, 3vh, 1.75rem)`), a propósito — con centrado vertical puro el contenido queda con mucho aire arriba Y abajo en viewports altos, que es justo lo que no se quería (2026-09-09).
- **Formulario "glass"**: `.login-form-card` NO es una tarjeta blanca — es translúcida sobre el fondo oscuro (`background: rgba(255,255,255,0.07)` + `backdrop-filter: blur(20px)` + borde sutil claro), con texto blanco/claro y los `input` restilizados en el mismo tono (fondo translúcido, borde claro, texto blanco). El objetivo es que el formulario se sienta parte del mismo diseño que el panel de arriba (mismo family Sora en el `<h1>`), no un componente ajeno pegado encima. Cualquier formulario que en el futuro viva sobre un fondo oscuro debe seguir este mismo patrón (`.login-form-card` como referencia), no el `.card`/`.field input` genérico pensado para fondos claros.
  - **El mismo criterio aplica a cualquier botón, no solo a los inputs** (bug real encontrado y corregido 2026-09-09, Sprint 7 "Entrar con Face ID"): `.btn-secondary` normal usa `var(--surface-2)`/`var(--text)` (tokens del tema claro/oscuro del usuario) — como `.login-shell` tiene el fondo oscuro fijo **desacoplado** de ese toggle, un `.btn-secondary` sin más se veía como una píldora blanca sólida rompiendo el "glass" en cualquier tema. Se agregó `.login-form-card .btn-secondary` con el mismo tratamiento translúcido que los inputs (`rgba(255,255,255,0.07)` + borde claro + texto blanco). Cualquier botón secundario nuevo dentro de `.login-form-card` hereda esto automáticamente — no hace falta repetirlo por botón.
- **Sin scroll, a propósito**: `.login-shell` usa `position: fixed; inset: 0;` — esto es intencional y necesario, no cosmético. `MainLayout` envuelve TODAS las rutas (incluida `/login`, que no tiene `[Authorize]`) en `.app-content`, que trae padding pensado para páginas autenticadas (top/bottom generoso, `padding-bottom:6rem` en móvil para dejar espacio al nav inferior fijo). Ese padding sumaba altura extra y forzaba scroll vertical en el login. `position:fixed; inset:0` saca la sección del flujo del documento por completo, ignorando ese padding, y la fija exactamente al viewport. Todo el interior (`.login-section`) usa `clamp()` en gaps/tamaños de fuente para comprimirse en viewports bajos sin necesitar scroll.
- **Tarjetas flotantes nunca deben tapar el formulario NI el encabezado — ni recortarse**: hubo dos rondas de este bug. Ronda 1: solo `overflow: hidden` en `.login-visual-stage` (recortaba las tarjetas en vez de dejarlas invadir lo de abajo, pero se veían "cortadas"). Ronda 2 (causa raíz real, corregida 2026-09-09): el motor "parallax stage" no acotaba `dx`/`dy` (ver sección del patrón arriba) — como el cursor podía estar muy por fuera del stage (ej. hasta el fondo de la página), el desplazamiento crecía sin límite y la tarjeta se salía cada vez más del `overflow:hidden`, viéndose "perdida"/recortada más y más mientras el cursor se alejaba. La corrección definitiva fue acotar `dx`/`dy` a `[-1,1]` en `parallaxStage.js` (ya no es específico del login, beneficia cualquier uso futuro del patrón). Además se agrandó el `.login-visual-stage` a `clamp(140px, 19vh, 175px)` de alto (antes ~110px) y el `gap` de `.login-section` a `clamp(0.75rem, 2.8vh, 1.4rem)`, dando margen real de sobra. Con el clamp puesto, `overflow: hidden` en el stage queda como **red de seguridad** que en el uso normal nunca debería activarse ni notarse — no es el mecanismo que resuelve el problema, solo un respaldo.
- El `depthStep` del efecto parallax en este contexto compacto se pasa en 3 (`parallaxStage.init(..., 3)`), más sutil que el default de 7.
- Tipografía del headline: **Sora** (Google Fonts, licencia SIL Open Font — libre de usar), cargada vía `<link>` a `fonts.googleapis.com` en `index.html`. El resto de la app sigue con la pila de fuentes del sistema (SPEC-005 original); Sora está acotada al login por ahora.
- **Interacción táctil (móvil)**: el motor "parallax stage" escucha `pointermove`, que en pantallas táctiles solo se dispara mientras el dedo está tocando y moviéndose (arrastrar) — no hay efecto por solo tener el teléfono abierto, ni por inclinarlo. Sin arrastrar, las tarjetas quedan quietas en su posición base (el abanico). Decisión explícita del usuario (2026-09-09): dejarlo así, sin inclinación por giroscopio ni desactivar la interacción en móvil.
- **Touch fluido, no "atrasado" respecto al dedo** (bug real corregido 2026-09-09): en la primera versión, arrastrar el dedo se sentía notablemente menos fluido que mover el mouse. Dos causas, ambas corregidas en el motor genérico (no son parches solo del login):
  1. `.login-visual-stage`/`.login-visual-copy` no tenían `touch-action: none` — el navegador se tomaba un instante para decidir si el arrastre era un gesto de scroll/zoom antes de entregarle los eventos a JS, y de paso podía activar selección de texto nativa sobre el encabezado. Se agregó `touch-action: none` + `user-select: none` a ambos.
  2. `.parallax-item` tiene `transition: transform 0.15s ease-out` para que el mouse (que manda eventos muy seguidos) se sienta suave. En touch, los eventos llegan más espaciados, y esa misma transición hacía que la tarjeta se sintiera "persiguiendo" al dedo en vez de pegada a él. `parallaxStage.js` ahora lee `e.pointerType` en cada `pointermove` y, si es `'touch'`, pone `item.style.transitionDuration = '0s'` (seguimiento 1:1, inmediato); en mouse deja la transición del CSS intacta (`transitionDuration = ''`). Cualquier uso nuevo del patrón "parallax stage" hereda este comportamiento automáticamente.
- **Tag "tarjetas de crédito" oculto, no eliminado**: el `<span class="tag tag-oculto">` se dejó en el markup con `visibility: hidden` (no `display:none` ni se borró del DOM) — a propósito, para que su alto siga reservando el mismo espacio y el encabezado "Tu dinero, bajo control." no se recorra hacia arriba. Cualquier ajuste futuro de "quitar texto sin mover el resto del layout" debe usar `visibility:hidden` sobre el elemento, nunca quitarlo del árbol.
- **`Register.razor` unificado con este mismo diseño** (2026-09-09): ambas pantallas (`/login` y `/register`) comparten el componente `Components/AuthShell.razor` — panel visual (tag oculto + headline + subtítulo + `.login-visual-stage` con las 3 tarjetas) parametrizado (`HeadlineLinea1`, `HeadlineLinea2`, `Subtitulo`) más un `ChildContent` para el formulario propio de cada página. `AuthShell` es quien llama `parallaxStage.init` una sola vez — las páginas ya no lo hacen. Cualquier pantalla nueva de auth (recuperar contraseña, etc.) debe envolver su formulario en `<AuthShell>` en vez de reconstruir el layout a mano.
- **Bug real reportado por el usuario probando en su celular (2026-09-10): a veces aparecía scroll vertical después de escribir en los campos y enviar el formulario.** Causa raíz: `.login-shell` ya era `position:fixed;inset:0`, pero `html`/`body` no tenían ningún límite de alto propio — en iOS/Android, cuando el teclado táctil aparece para un input enfocado, el navegador puede desplazar el viewport visual para mantener visible ese input, y ese desplazamiento a veces se quedaba pegado como scroll real del documento aunque el teclado se cerrara después. Corregido con una clase `body.auth-route` (`overflow:hidden; height:100%; position:fixed; width:100%`) que `AuthShell.razor` agrega a `document.body` al montarse y quita en `DisposeAsync` — bloquea el scroll del documento completo solo mientras una pantalla de auth está activa, sin afectar el resto de la app (que sí necesita scroll normal).
- **El `<h1>` del formulario no debe quedar "marcado" al cargar la página** (bug real corregido 2026-09-09): `App.razor` tiene `<FocusOnNavigate Selector="h1" />` (accesibilidad estándar de Blazor: le avisa a lectores de pantalla dónde empieza el contenido de la página nueva). Eso deja un contorno de foco del navegador visualmente pegado al `h1` ("Bienvenido"/"Crea tu cuenta") después de cada carga/recarga. La corrección es CSS global (`h1:focus { outline: none; }` en `app.css`), no quitar `FocusOnNavigate` — el `h1` tiene `tabindex="-1"` así que un usuario de teclado nunca llega ahí tabulando, quitar el contorno no afecta accesibilidad real, solo el artefacto visual.

## Sidebar / navegación: identidad del usuario

- En el nav lateral de escritorio (`.side-nav`), debajo de los enlaces de navegación, va una tarjeta de usuario fija al fondo: fila con iniciales en avatar circular + nombre (`Nombres` del perfil, o el correo si no hay nombre capturado), y debajo un botón **"Cerrar sesión"** con el mismo estilo `.btn.btn-danger` que se usa en Configuración (nunca como link subrayado — ver corrección 2026-09-08). En el nav inferior de móvil no se repite (por espacio); el acceso a sesión/perfil vive en Configuración.
- El saludo del Dashboard ("Hola, {Nombres}") usa el mismo dato de perfil. Si el usuario no ha capturado su nombre, se muestra "Hola" a secas (sin coma ni placeholder feo) y una invitación sutil a completarlo en Configuración.

## Dashboard: alcance

- El Dashboard **no** muestra el listado/pila de tarjetas (se decidió quitarlo el 2026-09-08 por redundancia con el módulo Tarjetas) — se limita al widget "¿Qué tarjeta uso hoy?" y a lo que se defina en sprints futuros (recordatorios de pago, score resumido, etc. — ver backlog en sprints.md). El listado completo de tarjetas vive únicamente en `/tarjetas`.

## Tarjetas apiladas ("stack")

- Tanto el Dashboard como el módulo de Tarjetas muestran las tarjetas del usuario en una pila visual (`.tarjetas-stack`): cada `.credit-card-visual` se solapa con la siguiente dejando ver solo una franja superior (~54px), similar a un wallet físico/Apple Wallet. Al hacer hover/focus sobre una tarjeta de la pila, esa tarjeta se eleva (mayor `z-index`, `translateY` hacia arriba, sombra más marcada) para poder leerla completa sin necesidad de scroll largo.
- Con 1 sola tarjeta no hay efecto de pila (se muestra completa, tamaño normal).
- El botón "Dar de baja" NO va pegado a la pila como bloque separado: vive dentro de la propia tarjeta (aparece al elevarla/hacer hover, o siempre visible en un rincón discreto de cada card) para que quede claro que la acción es individual por tarjeta.
- Espaciado: siempre debe haber separación clara (mínimo `1.5rem`) entre el botón "+ Agregar tarjeta" y el inicio de la pila — nunca deben verse pegados.

## Alta y edición de tarjeta: formulario con vista previa en vivo

- El alta y la edición de una tarjeta usan el **mismo componente** (`TarjetaFormCard`): arriba del formulario se renderiza un `CreditCardVisual` de vista previa, enlazado en vivo a los campos que el usuario va llenando (alias, banco, últimos 4 dígitos, marca, color, día de corte). Cada tecla escrita actualiza la tarjeta visual al instante — no hay un paso separado de "confirmar" para ver cómo queda.
- En edición, el formulario llega prellenado con los valores actuales de la tarjeta y el botón dice "Guardar" sobre un `PUT /api/creditcards/{id}` en vez de `POST`.
- Cada tarjeta en el listado/pila tiene sus propios íconos de **editar** (lápiz) y **dar de baja** (papelera) en la esquina superior derecha — nunca un botón de acción compartido fuera de la tarjeta.

**Gotcha de Blazor a evitar**: los componentes tipados `InputText`/`InputNumber` con `@bind-Value:event="oninput"` producen un `System.ArgumentException` en tiempo de ejecución en este proyecto (WASM, .NET 10) al escribir. Para binding "en cada tecla" (necesario para la vista previa en vivo) usar siempre el elemento nativo con `@bind`/`@bind:event="oninput"` (ej. `<input @bind="modelo.Nombre" @bind:event="oninput" />`), nunca el componente `InputText` con ese evento. `InputNumber`/`InputSelect` con el evento por defecto (`onchange`) sí son seguros.

## Personalización de tarjeta al crearla

- El formulario de alta de tarjeta incluye un selector de color (paleta de acentos predefinida + opción "personalizado" con color picker nativo). Si el usuario no elige color, el sistema autoasigna uno rotando una paleta fija según la cantidad de tarjetas que ya tiene (ver `ColorHex` en SPEC-002).
- La marca (Visa/Mastercard/American Express/Otra) ya se captura en el formulario; el `.credit-card-visual` renderiza un glifo SVG propio simple por marca (no logos oficiales con derechos reservados) para dar la referencia visual sin riesgo de marca registrada.

## Diálogos y notificaciones (SweetAlert2)

- Librería: **SweetAlert2** (CDN, `cdn.jsdelivr.net/npm/sweetalert2`), envuelta en un servicio JS interop propio (`wwwroot/js/dialogs.js` + `DialogService` en C#) para no repetir configuración en cada página.
- **Confirmación antes de eliminar/dar de baja**: siempre pasa por un diálogo SweetAlert2 modal (`Swal.fire`) con esquinas redondeadas (`borderRadius` vía `customClass`, no el default cuadrado de SweetAlert), texto claro de qué se va a eliminar, botón de confirmar en rojo/alerta (`--danger`) y cancelar neutro. Nunca se elimina nada sin ese paso.
- **Errores y validaciones**: se muestran como **toast** de SweetAlert2 (`Swal.mixin({ toast: true, position: 'top-end', timer: 3500, showConfirmButton: false })`), no como modal bloqueante. Colores discretos y legibles, no neón: fondo `--surface`, texto `--text`, barra/ícono en `--danger` (error) o `--success` (confirmación), acorde a la paleta clara/oscura vigente — nunca los rojo/verde saturados por defecto de SweetAlert.
- Todo diálogo/toast respeta el tema activo (claro/oscuro) leyendo las mismas variables CSS de la app.

## Idioma: todo mensaje visible al usuario debe estar en español

- **Regla general**: cualquier texto que el usuario pueda leer en la app (labels, botones, toasts, diálogos, mensajes de error/validación) debe estar en español. Esto ya se cumplía en todo el markup propio de `.razor` desde el inicio del proyecto — la brecha real encontrada (2026-09-09) estaba en los **mensajes de error que vienen del propio ASP.NET Core Identity**, no de código propio.
- **Causa raíz**: `MapIdentityApi<ApplicationUser>()` (endpoints `/api/auth/register` y `/api/auth/login`) valida contraseña/correo con `UserManager`, que arma sus mensajes de error a través de `IdentityErrorDescriber`. La implementación default de ese describer trae los textos **hardcodeados en inglés** (ej. "Passwords must have at least one non alphanumeric character.", "Email 'x' is already taken.") — no se localizan solos aunque el resto de la app esté en español, porque no son recursos `.resx` sensibles a cultura, son strings literales en el código de Identity. El cliente (`AuthService.ExtraerErroresAsync`) toma esos mensajes tal cual del `ProblemDetails` y los muestra en un toast — por eso se veían en inglés en Login/Register pese a que todo el resto del formulario está en español.
- **Corrección**: `DescriptorErroresIdentityEspanol` (`src/TarjetasCredito.Infrastructure/Identity/DescriptorErroresIdentityEspanol.cs`) — subclase de `IdentityErrorDescriber` que sobreescribe **todos** los métodos con el mensaje en español equivalente, registrada en el Server vía `.AddErrorDescriber<DescriptorErroresIdentityEspanol>()` sobre `AddIdentityApiEndpoints<ApplicationUser>()`.
- **Cualquier integración futura que dependa de una librería de terceros con mensajes propios en inglés** (ASP.NET Core Identity, un SDK de buró de crédito real, etc.) debe revisarse con el mismo criterio: si expone un punto de extensión para sobreescribir los textos (como `IdentityErrorDescriber`), úsalo; si no lo expone, el mensaje debe traducirse/envolverse en la capa que lo consume antes de mostrarlo al usuario — nunca dejar pasar un mensaje de una dependencia externa sin verificar su idioma primero.
- **Segunda brecha real encontrada y corregida (2026-09-09): un toast mostró literalmente "Unauthorized".** `AuthService.IniciarSesionAsync` reenviaba `ProblemDetails.Title` tal cual del `/api/auth/login` fallido — a diferencia de Registrar, un login fallido de `MapIdentityApi` **no pasa por `IdentityErrorDescriber`** (no hay campos que validar, es solo "sí/no"), así que ese `Title` es el `ProblemDetails` genérico de ASP.NET Core, con el reason-phrase default del status code (401 → "Unauthorized", en inglés, no traducible vía `DescriptorErroresIdentityEspanol`). Corregido usando un mensaje fijo en español ("Correo o contraseña incorrectos.") en vez de reenviar nada del servidor para este caso — además evita revelar si el correo existe o la contraseña es la que está mal (buena práctica de seguridad). Se hizo una auditoría completa de los ~20 sitios que muestran toasts en la app (`Dialogs.ToastErrorAsync`/`ToastExitoAsync`/`ConfirmarAsync`) para encontrar el mismo patrón de riesgo en otros lados; se encontraron dos más:
  - `AuthService.ExtraerErroresAsync` (usado solo por `RegistrarAsync`) tenía el mismo *fallback* a `problema.Title` por si el cuerpo no traía un diccionario `Errors` — se quitó y se reemplazó por un mensaje fijo en español, mismo criterio que el login.
  - `Compras.razor`/`TarjetaFormCard.razor` mostraban `await response.Content.ReadAsStringAsync()` crudo en el toast de error al fallar un `POST`/`PUT`. Aunque los formularios actuales del Client nunca mandan un valor que dispare el problema (los campos requeridos siempre llegan como `""`, no `null`), los DTOs en `Shared/Dtos/` no tienen ninguna anotación `[Required]`, así que **cualquier otra forma de llegar a ese mismo endpoint** (Swagger, un JSON malformado, un enum fuera de rango) hace que `[ApiController]` dispare su `ValidationProblemDetails` automático **antes** de que corra el código propio del controller — ese cuerpo es JSON en inglés, no el `BadRequest("mensaje")` en español que sí escribe la app. Corregido con `Services/ErrorMessageHelper.ExtraerMensajeAsync(response, mensajePorDefecto)`: solo se confía en el cuerpo de la respuesta cuando su `Content-Type` es `text/plain` (la forma en que ASP.NET Core serializa un `BadRequest(string)` — la única vía por la que este código realmente escribe un mensaje) — cualquier otro `Content-Type` (`application/problem+json` del validador automático, cuerpo vacío de un `NotFound()`, etc.) usa el mensaje genérico en español que pasa el caller, nunca el cuerpo crudo. Cualquier nuevo llamado a un endpoint que pueda fallar debe usar este helper en vez de leer `response.Content.ReadAsStringAsync()` directo.

## Patrón reutilizable: estados de carga y estados vacíos (Sprint 9)

**Decisión (2026-09-10)**: se reemplazó el `<p class="text-muted">Cargando...</p>` genérico y las líneas sueltas de "no hay datos todavía" (repetidas en cada página) por dos componentes reusables, mismo criterio que `EstadoSinConexion` (ya existente desde Sprint 27) para "falló la conexión".

- **`Components/EstadoCarga.razor`**: placeholder tipo *skeleton* — filas con un círculo + dos líneas (silueta genérica aplicable a tarjetas, compras, recordatorios, factores de buró) con un barrido sutil de brillo (`@keyframes skeleton-shimmer`, respeta `prefers-reduced-motion: reduce` igual que `.entrada-suave`). Parámetro `Cantidad` (int, default 3) controla cuántas filas placeholder se muestran — usar un número parecido a lo que normalmente aparece en esa lista (ej. `Cantidad="2"` en Tarjetas/Dashboard, `Cantidad="1"` en las listas cortas de Configuración).
- **`Components/EstadoVacio.razor`**: icono (mismo emoji que usa esa sección en el nav) + título + descripción + `ChildContent` opcional para un botón/link de acción — en vez de una sola línea de texto plano. Se usa cuando la lista cargó bien pero está genuinamente vacía (0 tarjetas, 0 compras, 0 recordatorios), nunca para errores de conexión (eso sigue siendo `EstadoSinConexion`).
- **Gap real encontrado al hacer este barrido**: `Tarjetas.razor` no tenía absolutamente ningún estado vacío — con 0 tarjetas activas simplemente renderizaba un `.tarjetas-stack` vacío sin ningún mensaje. Corregido como parte de este mismo sprint.
- Cualquier página nueva que cargue una lista debe usar `<EstadoCarga Cantidad="N" />` mientras `cargando` es `true`, y `<EstadoVacio Icono="..." Titulo="..." Descripcion="...">` (con `ChildContent` si aplica una acción) cuando la carga tuvo éxito pero la lista viene vacía — en vez de reinventar un `<p class="text-muted">` suelto.
- Los ítems de una lista ya cargada (`.card-interactive`) también llevan `.entrada-suave` individualmente (antes solo el contenedor principal de la página tenía la animación de entrada) — micro-interacción menor pero consistente: cada fila nueva (compra, recordatorio, factor de buró) se desliza/aparece igual que las tarjetas principales.

## Micro-interacción: feedback táctil en botones

`.btn:active:not(:disabled) { transform: scale(0.97); }` (Sprint 9) — cualquier botón (`.btn`, `.btn-secondary`, `.btn-danger`) se encoge levemente al presionarlo, antes de que la acción real complete. Se suma al `transform: translateY(-1px)` que ya existía en `:hover`; ambos comparten la misma `transition` ya declarada en `.btn`, no hace falta agregar nada al usar la clase normal.

## Patrón reutilizable: overlay de carga bloqueante

**Decisión (Sprint 31, 2026-09-10)**: para una operación de **un solo paso sin vuelta atrás** que además cambia lo que puede hacer el resto de la pantalla (ej. la ceremonia de Face ID en el login, que si tiene éxito navega a otra página) no basta con que el propio botón diga "Verificando..." y se deshabilite a sí mismo — el usuario podía seguir escribiendo en los campos de correo/contraseña o tocar otra cosa mientras la ceremonia biométrica seguía en curso (bug real reportado por el usuario probando en su celular). `Components/OverlayBloqueante.razor` cubre **toda la pantalla** (no solo el formulario) con un fondo oscuro translúcido + spinner + mensaje, y captura todos los clicks/touches (`pointer-events:auto`, `z-index` alto) mientras `Mostrar="true"`.

**Uso**: `<OverlayBloqueante Mostrar="@enviandoAlgo" Mensaje="Verificando..." />`, colocado como hermano del contenido de la página (no anidado dentro de un contenedor con `overflow`/`position` propios, para que el `position:fixed;inset:0` cubra realmente toda la pantalla). Además de la barrera visual, los campos/botones relevantes también deben llevar `disabled="@enviandoAlgo"` como defensa adicional (evita que un usuario de teclado llegue a ellos por Tab). Primer uso: el botón "Entrar con Face ID" del login — cualquier operación futura de un solo paso similar (ej. "Agregar Face ID" en Configuración) debería adoptar el mismo patrón en vez de solo deshabilitar su propio botón.

## Spinner de carga inicial de la app (arranque de Blazor WASM)

`.loading-progress`/`.loading-progress-text` (`index.html` + `app.css`) son el spinner que Blazor muestra mientras descarga el runtime WASM, antes de que la app en sí exista. **Bug real reportado por el usuario probando en su celular (2026-09-10)**: el porcentaje/texto ("Cargando"/"73%") no quedaba centrado dentro del círculo — venían del template default de .NET, que posiciona el texto con un cálculo de número mágico (`inset: calc(40vh + 3.25rem) 0 auto 0`) que no coincide realmente con el centro del círculo. Corregido haciendo que `.loading-progress-text` use exactamente la misma caja que `.loading-progress` (mismo `inset`/`width`/`height`/`margin`) y centrando el texto con flexbox dentro de esa caja, en vez de intentar calcular la posición a mano.

## Bloqueo de zoom táctil

**Decisión (Sprint 33, 2026-09-10)**: la app bloquea el gesto de pellizco-para-zoom en todo momento — `maximum-scale=1.0, user-scalable=no` en el `<meta name="viewport">` de `index.html` (mecanismo principal) + `touch-action: pan-x pan-y` en `html, body` (refuerzo en CSS, no afecta el scroll/paneo normal de cada página). **Bug real reportado por el usuario probando en su celular**: al hacer zoom con los dedos, o simplemente al enfocar/cerrar el teclado táctil (que también dispara un cambio de escala del viewport en iOS/Android), la app perdía su encuadre fijo y quedaba con scroll libre en las cuatro direcciones — rompía por completo la sensación de "app instalada" en cualquier pantalla, no solo login.

**Trade-off de accesibilidad, asumido a propósito**: deshabilitar el zoom del usuario contradice WCAG 1.4.4 (el usuario no puede ampliar contenido si lo necesita) — es una decisión de producto explícita del usuario para que la PWA se sienta como app nativa, no un descuido. Si en algún momento se reporta que esto afecta a un usuario que sí necesita zoom, hay que revisar esta decisión con el usuario antes de revertirla.
