# SPEC_TarjetasCredito-004-Seguridad

## Estado: Vigente (2026-09-08)

## Autenticación

- Registro e inicio de sesión **por correo electrónico** vía ASP.NET Core Identity (`UserManager<ApplicationUser>` + `MapIdentityApi<ApplicationUser>()`). Confirmación de correo requerida antes de poder iniciar sesión en producción (en desarrollo se puede omitir para agilizar pruebas, documentado en `appsettings.Development.json`).
- Tokens **bearer opacos** (cifrados con ASP.NET Core Data Protection, NO JWT) de vida corta + refresh token, almacenados en el cliente WASM (memoria + `localStorage` para el refresh token). No se usan cookies porque el cliente es un SPA/WASM standalone servido posiblemente desde otro origen que el API en producción. Como el token es opaco, el cliente NO puede decodificar claims de él: el `ClaimsPrincipal` para la UI se construye llamando a `GET /api/profile` ("quién soy") con el token ya adjunto, nunca parseando el token.
- `TokenAuthenticationStateProvider.IntentarRestaurarSesionAsync` envuelve la llamada de red en try/catch: si el Server no responde (caído, sin conexión), la app degrada a "sesión no restaurada" y muestra el login — nunca debe quedarse en una pantalla de carga infinita ni tronar con una excepción no controlada por un fallo de red al arrancar (bug real encontrado y corregido el 2026-09-08).
- **FaceID / biometría**: se implementa vía **WebAuthn** (`navigator.credentials`), no vía una librería propietaria de Apple/Google. WebAuthn con autenticador de plataforma (Face ID en iOS/macOS, Windows Hello, huella en Android) es el estándar web soportado por todos los navegadores modernos y es lo que realmente puede pedir "Face ID" a través de un PWA. Se registra como **método de acceso rápido** desde Configuración, después de que el usuario ya se autenticó al menos una vez por correo+contraseña — WebAuthn nunca reemplaza el registro inicial por correo (Sprint 7, 2026-09-09).
  - **Soporte nativo de .NET 10, sin librerías de terceros**: confirmado por inspección directa de los ensamblados del SDK instalado (10.0.11) — `SignInManager<TUser>`/`UserManager<TUser>` de ASP.NET Core Identity ya traen los métodos de la ceremonia WebAuthn completa (`MakePasskeyCreationOptionsAsync`, `PerformPasskeyAttestationAsync`, `MakePasskeyRequestOptionsAsync`, `PerformPasskeyAssertionAsync`, `AddOrUpdatePasskeyAsync`, `GetPasskeysAsync`, `RemovePasskeyAsync`), y el store EF Core (`IdentityUserPasskey<TKey>`) ya es parte de `IdentityDbContext<ApplicationUser>` — no se agregó ni se debe agregar `Fido2NetLib` ni criptografía WebAuthn manual. Lo único que `MapIdentityApi<ApplicationUser>()` **no** trae en esta versión del SDK son los endpoints HTTP `/passkey/*` — están escritos a mano en `PasskeyEndpoints.cs` llamando directo a los métodos nativos de arriba (ver SPEC-001, sección de excepción minimal-API).
  - **UX de un solo botón, sin pedir correo primero**: "Entrar con Face ID" usa una credencial "discoverable" (`MakePasskeyRequestOptionsAsync(user: null)`) — el propio navegador muestra el selector de cuenta, no hay un paso intermedio de escribir el correo. Es la UX estándar moderna de passkeys.
  - **Interop JS sin conversión manual de bytes**: se apoya en `PublicKeyCredential.parseCreationOptionsFromJSON()`/`.parseRequestOptionsFromJSON()` y `credential.toJSON()` (extensión "JSON serialization" de WebAuthn nivel 3, ya soportada por navegadores modernos) — las opciones que genera el servidor y la credencial que produce el navegador viajan como JSON crudo en ambas direcciones, sin que el JS tenga que convertir `ArrayBuffer`↔base64 a mano.
  - **`IdentityPasskeyOptions.ServerDomain`**: se configura explícitamente (no se deja en default) porque el RP ID de WebAuthn debe coincidir con el dominio real donde vive el Client. En desarrollo, `"localhost"` sirve para `https://localhost:7160` (Client) y `https://localhost:7287` (Server) porque comparten hostname (el RP ID ignora el puerto). En producción debe ser el dominio real del Client, sin protocolo ni puerto (ej. `tarjetascredito.com`), configurable vía `WebAuthn:ServerDomain`.
  - **Bug real encontrado y corregido (2026-09-09): la tabla de passkeys no aparecía sola en la migración.** `IdentityDbContext<ApplicationUser>` (la sobrecarga de un solo parámetro genérico que ya usábamos) sí hereda, por cadena de clases base, hasta la sobrecarga completa de 9 parámetros que incluye `IdentityUserPasskey<string>` como `TUserPasskey` — confirmado por reflexión sobre el ensamblado real. Sin embargo esa entidad **no queda incluida en el modelo de EF Core por convención** (`dotnet ef migrations add` generaba una migración vacía) — hay que declararla a mano en `AppDbContext.OnModelCreating`: `builder.Entity<IdentityUserPasskey<string>>(e => { e.HasKey(p => p.CredentialId); e.HasIndex(p => p.UserId); e.OwnsOne(p => p.Data); })` (`CredentialId` es único por diseño de WebAuthn y se usa como llave; `Data` es un tipo `IdentityPasskeyData` que EF Core necesita como owned type, si no lo declaramos como tal falla con "requiere una llave primaria"). Cualquier entidad nativa de Identity que aparezca en sprints futuros (ej. si se usa `TwoFactorEnabled`/tokens de recuperación con tablas propias) debe verificarse de la misma forma — no asumir que "está en la clase base" significa "está en el modelo".
  - **También se detectó y corrigió un desfase de versión en las herramientas**: la herramienta global `dotnet-ef` estaba en `10.0.10` mientras el proyecto referencia EF Core `10.0.11` — con ese desfase, `dotnet ef migrations add` también producía una migración vacía (sin siquiera el error de llave primaria). Se corrigió con `dotnet tool update --global dotnet-ef --version 10.0.11`. Si una migración nueva sale sospechosamente vacía, verificar primero `dotnet ef --version` contra la versión de `Microsoft.EntityFrameworkCore.Design` del proyecto antes de asumir que "no hay cambios que migrar".
  - **Bug real encontrado por el usuario probando en su propio dispositivo (2026-09-09): "No passkey attestation is underway" al intentar registrar el Face ID.** Causa raíz confirmada decompilando `SignInManager<TUser>` (`ilspycmd`, no adivinado): `MakePasskeyCreationOptionsAsync`/`MakePasskeyRequestOptionsAsync` guardan el reto de la ceremonia (`AttestationState`/`AssertionState`) en una **cookie efímera**, reutilizando el esquema de cookie de 2FA de Identity (`Context.SignInAsync(IdentityConstants.TwoFactorUserIdScheme, ...)`); `PerformPasskeyAttestationAsync`/`PerformPasskeyAssertionAsync` la leen de vuelta con `Context.AuthenticateAsync(IdentityConstants.TwoFactorUserIdScheme)`. Como Client (`:7160`) y Server (`:7287`) son orígenes distintos, esa cookie nunca volvía: (a) el `HttpClient` de Blazor WASM no manda credenciales en peticiones cross-origin salvo que se pida explícitamente, y (b) aunque se pidiera, la cookie se emitía sin `SameSite=None`/`Secure`, que es obligatorio para que un navegador la entregue cross-origin. Corrección en dos partes:
    1. **Servidor** (`Program.cs`): `builder.Services.Configure<CookieAuthenticationOptions>(IdentityConstants.TwoFactorUserIdScheme, o => { o.Cookie.SameSite = SameSiteMode.None; o.Cookie.SecurePolicy = CookieSecurePolicy.Always; })`.
    2. **Cliente** (`PasskeyApiService.cs`): las 4 llamadas que participan en la ceremonia (opciones de registro/acceso + registro/acceso) arman su propio `HttpRequestMessage` y llaman `request.SetBrowserRequestCredentials(BrowserRequestCredentials.Include)` antes de `http.SendAsync(...)` — los métodos de conveniencia (`PostAsJsonAsync`, etc.) no exponen esa opción. Listar/eliminar credenciales no participan de la ceremonia y no lo necesitan.
    - La política CORS (`AddCors` en `Program.cs`) ya tenía `.AllowCredentials()` con `WithOrigins(...)` explícito (nunca `AllowAnyOrigin()`, que es incompatible con credenciales) — no hizo falta tocarla, solo faltaba que el cliente y la cookie realmente pidieran/permitieran viajar con credenciales.

## Privacidad del login en dispositivos compartidos

- El formulario de login/registro (`Login.razor`/`Register.razor`) **no debe insinuar ni revelar quién usó la sesión anteriormente** en ese dispositivo — es una app financiera y puede haber más de una persona usando la misma laptop/PC. Los campos de correo y contraseña llevan `autocomplete="off"` (en el `<EditForm>` y en cada `<input>`) para evitar que el navegador prellene el correo o muestre un dropdown de sugerencias con correos usados antes en ese formulario (Sprint 28, 2026-09-09, decisión explícita del usuario).
- **No se bloquea que el navegador guarde contraseñas**: el propio gestor de contraseñas del navegador puede seguir ofreciendo "¿Guardar contraseña?" después de un login exitoso — eso es aceptable y deseable, el usuario decide si lo usa. Lo que se evita es que la *pantalla* de login sugiera/revele visualmente un acceso anterior con solo abrirla — no el guardado en sí. Por eso el campo de contraseña **no** usa `autocomplete="new-password"` (eso sí bloquearía el guardado); solo `off`.
- **Bug real confirmado por el usuario (2026-09-09): `autocomplete="off"` por sí solo no bastó.** Tal como se anticipó ("limitación conocida de los navegadores"), Chrome sí lo ignoró en la práctica: tras cerrar sesión, el login volvía a aparecer con el correo y la contraseña del usuario anterior ya rellenados. Se corrigió con una técnica más contundente, no solo el atributo: los campos de correo y contraseña nacen con `readonly` (el navegador no autocompleta un campo de solo lectura al cargar la página) y un `onfocus="this.removeAttribute('readonly')"` **en HTML plano, no un `@onfocus` de Blazor** — se quita el `readonly` de forma síncrona en el propio evento del navegador, sin esperar un round-trip de Blazor, así el campo ya es editable normalmente antes de que el usuario alcance a escribir la primera letra. Con esto los campos quedan genuinamente vacíos al cargar la página, sin depender de que el navegador decida respetar una simple sugerencia.
- **Limitación conocida de los navegadores, no del sitio**: incluso con `readonly`, un usuario puede hacer clic manualmente y el navegador podría mostrarle su propio dropdown de sugerencias para que él mismo elija un correo guardado — eso es una acción explícita del usuario sobre su propio gestor de contraseñas, no la página revelando algo sin que él la toque, y no es algo que el sitio pueda ni deba bloquear.
- **Face ID es el mecanismo recomendado de acceso rápido en dispositivos compartidos** (Sprint 7): en vez de depender de que el navegador autocomplete visiblemente el correo/contraseña, "Entrar con Face ID" permite reingresar sin mostrar ni escribir ninguna credencial — la verificación es biométrica/PIN local y nunca expone el correo en pantalla. Es la razón por la que se priorizó implementar WebAuthn antes de este ajuste.

## Aislamiento de datos por usuario

- Cada endpoint de tarjetas/compras/recordatorios/buró exige `[Authorize]` y filtra explícitamente por `UserId` extraído del claim del token (`ClaimTypes.NameIdentifier`), nunca por un `userId` recibido del cliente en el body/query. Ver detalle en [SPEC_TarjetasCredito-002-BaseDeDatos.md](SPEC_TarjetasCredito-002-BaseDeDatos.md).
- Los repositorios de `Infrastructure` reciben el `UserId` del contexto autenticado inyectado por el Server, nunca confían en un valor pasado libremente.

## Datos sensibles

- Nunca se almacena el número completo de tarjeta, CVV ni PIN. Solo últimos 4 dígitos, banco, marca, límite, fechas de corte/pago y tasa (campos necesarios para las recomendaciones).
- Connection strings y API keys (VAPID para push, futura API de buró, futura API de Claude) se manejan con `dotnet user-secrets` en desarrollo y variables de entorno/secret manager en producción. Nunca se commitean.

## Transporte

- HTTPS obligatorio en todos los entornos, incluido `dotnet run` local (requisito duro de WebAuthn y Web Push, que no funcionan sobre HTTP salvo `localhost` en algunos navegadores — no se debe depender de esa excepción).

## Notificaciones push

- Web Push estándar (VAPID). Las claves privadas VAPID se generan una vez y se guardan como secreto de servidor, nunca en el cliente.
- **Sin soporte nativo de .NET, a diferencia de passkeys**: confirmado por búsqueda exhaustiva (strings `Vapid`/`WebPush`/`PushSubscription`/`aes128gcm`) en todos los ensamblados de `Microsoft.AspNetCore.App` y `Microsoft.NETCore.App` 10.0.11 — cero coincidencias. Se usa el paquete NuGet **`WebPush` 1.0.13** (`web-push-libs/web-push-csharp`, puerto en C# del `web-push` de Node, target nativo `net10.0`, única dependencia transitiva `Portable.BouncyCastle` para el cifrado RFC 8291). API verificada por reflexión contra el DLL real antes de usarla: `VapidHelper.GenerateVapidKeys()`, `WebPushClient.SendNotificationAsync(PushSubscription, payloadJson, VapidDetails, ct)`, `WebPushException.StatusCode` (404/410 = suscripción caducada, se poda de la base).
- **Claves VAPID**: se generan una sola vez con `VapidHelper.GenerateVapidKeys()` (ejecutado desde un proyecto de consola desechable, nunca desde el proyecto real) y se guardan con `dotnet user-secrets` en desarrollo (`WebPush:VapidPublicKey`, `WebPush:VapidPrivateKey`, `WebPush:Subject`) — `TarjetasCredito.Server` no tenía `<UserSecretsId>` configurado hasta este sprint, se inicializó con `dotnet user-secrets init`. La clave pública sí se expone al cliente (`GET /api/pushsubscriptions/vapid-public-key`, es pública por diseño del protocolo); la privada nunca sale del Server. En producción, variables de entorno/secret manager, igual que el resto de credenciales (ver "Datos sensibles" arriba).
- **Semántica de los 3 disparos por recordatorio** (decisión confirmada con el usuario, 2026-09-09): un aviso el día que llega `PaymentReminder.FechaOptimaPago` ("conviene pagar hoy para bajar tu utilización antes del corte"), y dos avisos sobre `FechaLimitePago` — 3 días antes y 1 día antes ("no dejes pasar tu fecha límite"). Cada uno se manda como máximo una vez por recordatorio, controlado por tres columnas nuevas (`NotificacionOptimaEnviadaUtc`/`NotificacionT3EnviadaUtc`/`NotificacionT1EnviadaUtc`, `null` = no enviado) para que el `PaymentReminderPushHostedService` (ver SPEC-001 y SPEC-003) sea idempotente entre ticks.
- **Suscripción**: el usuario activa notificaciones explícitamente desde Configuración (no se pide el permiso del navegador de forma automática/intrusiva al iniciar sesión) — mismo criterio de opt-in ya usado para Face ID. `PushSubscriptionRecord.Endpoint` tiene índice único: volver a suscribirse desde el mismo navegador actualiza la fila existente en vez de duplicarla.
- **`POST /api/pushsubscriptions/prueba`**: envía un push de prueba de inmediato a todas las suscripciones del usuario autenticado, sin pasar por `PaymentReminderPushHostedService` — botón "Enviar notificación de prueba" en Configuración (visible solo si ya está suscrito). Se agregó porque esperar a que el `BackgroundService` dispare un aviso real (solo al arrancar el Server o cada hora) hacía muy lento confirmar si las notificaciones realmente llegan; con este endpoint la confirmación es inmediata y, si falla, el mensaje de error incluye el `StatusCode` real que devolvió el servicio de push (útil para diagnosticar sin tener que leer logs del servidor).

## Buró de crédito

- Ninguna integración con un proveedor real de buró se activa sin credenciales explícitamente provistas por el usuario y sin mostrar un aviso de consentimiento antes de la primera consulta real.
